HYPERACTIVE STONE DUPLICATION IN NETWORK MODE
Root Cause Investigation Report
================================================================

ISSUE SUMMARY:
Hyperactive stones appear split/duplicated in network mode but not local mode.
The stone animates to its destination AND a separate fading copy appears at the 
source cell, making it look like the stone has duplicated and split.

SYMPTOM:
- Network snapshot applies
- Hyperactive stone with 'inherited_hyperactive_step_move' or 'ultimate_hyperactive_step_move' reason
- Animation engine correctly animates stone from source→destination
- BUT diff-renderer simultaneously renders destroy-fade at source cell
- Result: Stone appears split (ghost at source fading out, real stone at destination)

================================================================
ROOT CAUSE ANALYSIS
================================================================

PRIMARY ROOT CAUSE: **SNAPSHOT REPLAY TIMING RACE**
Location: ui/network/snapshot.js applySnapshot() vs diff-renderer rendering

The sequence of events causes a timing mismatch:

1. Network snapshot arrives with board state already in final position
2. snapshot.applySnapshot() is called:
   - Line 295: replaceObjectState('gameState', ...) ← Source cell now EMPTY
   - Line 296: replaceObjectState('cardState', ...)
   - Line 305: clearTransientPresentationQueues()
   - Line 322: emitPlaybackEvents(playbackEvents) ← Async via BoardOps.emitPresentationEvent
   - Line 326: refreshUi() ← Calls emitBoardUpdate() IMMEDIATELY
     └─ renderBoardDiff() is called SYNCHRONOUSLY
        - At this point, playback events NOT YET in cardState.presentationEvents queue
        - _hasPendingMoveSourceAtForDiff() returns FALSE
        - prevState has hyperactive marker, but marker comparison may not align
        - Falls through to destroy-fade logic (line 1610-1624)
        - CREATES SECOND FADING DISC AT SOURCE ❌

3. Then asynchronously:
   - BoardOps.emitPresentationEvent() adds event to queue (via cardState.presentationEvents.push)
   - AnimationEngine.play() receives event
   - Animates move correctly from source→destination ✓
   - After playback completes: emitBoardUpdate() called again
   - Second renderBoardDiff() sees events NOW, but damage already done

SECONDARY CONTRIBUTING FACTOR: **DUPLICATE DOM WRITERS**
The architecture has two independent systems updating the same DOM:
- AnimationEngine (animation-engine.js line 1871 handleMove):
  * Creates ghost from source disc
  * Hides source disc (visibility: hidden)
  * Animates ghost to destination
  * Shows disc at destination
- DiffRenderer (diff-renderer.js line 1603 updateCellDOM):
  * Compares previous vs current cell state
  * When source goes EMPTY→wants to add destroy-fade
  * Checks _hasPendingMoveSourceAtForDiff() but queue is stale

TERTIARY ISSUE: **STALE SOURCE EVENT DETECTION**
Lines 302-323 in diff-renderer.js (_collectPendingMoveSourceKeysForDiff):

`javascript
function _collectPendingMoveSourceKeysForDiff() {
    const keys = new Set();
    const pendingEntries = _getPendingPlaybackQueueEntriesForDiff();
    // ... extracts move sources from presentationEvents queue
}

function _hasPendingMoveSourceAtForDiff(row, col) {
    const keys = pendingMoveSourceKeysThisRender || _collectPendingMoveSourceKeysForDiff();
    return keys.has(key);
}
`

Problem: When _collectPendingMoveSourceKeysForDiff() runs:
- If events haven't been added to cardState.presentationEvents yet → returns empty set
- If events are being processed by AnimationEngine → queue state is uncertain
- The "pendingMoveSourceKeysThisRender" cache is reset per render but doesn't account
  for async queue population

CASE STUDY: Hyperactive Source-Empty Test (EXPECTED vs ACTUAL)

Test expects:
1. Snapshot applies: source=[3,3] EMPTY, dest=[4,3] has stone
2. Playback: reason='inherited_hyperactive_step_move'
3. Result: source cell empty (no disc), dest cell has disc

In network mode what happens:
1. ✓ Board state applied: gameState.board[3][3]=0, gameState.board[4][3]=1
2. ✓ Snapshot cardState applied with marker at [4,3]
3. ✓ renderBoardDiff() called immediately
   - prevState[3][3].value = 1 (had stone)
   - state[3][3].value = 0 (now empty)
   - currentDisc = null (source was already empty from fallback code path)
   - _hasPendingMoveSourceAtForDiff([3,3]) = FALSE ← Events not queued yet!
   - _hasHyperactiveLikeStateForDiff(prevState) = need to check marker
   - Falls through to destroy-fade path
   - ❌ Tries to add destroy-fade even though source already empty

4. ✓ emitPlaybackEvents() finally adds to queue (asynchronously)
5. ✓ AnimationEngine.play() handles move
6. ✓ Animation completes, second emitBoardUpdate()
7. ✓ renderBoardDiff() sees events now, but playback already done

WHY ONLY IN NETWORK MODE:

Local Mode (User Move):
- User clicks cell
- handleCellClick() processes move
- AnimationEngine.play() called first with playback events
- DiffRenderer only called after playback completes
- No race condition because presentation happens after animation setup

Network Mode (Snapshot):
- Network snapshot applies board state first (sync)
- emitBoardUpdate() called immediately (sync) ← triggers diff-renderer
- emitPlaybackEvents() called (async) ← adds to queue
- AnimationEngine.play() called (async) ← reads from queue
- Race: diff-renderer runs before animation engine is ready

================================================================
DETERMINING PRIMARY CAUSE
================================================================

The three candidate causes ranked by evidence:

1. **SNAPSHOT REPLAY TIMING** (PRIMARY - 85% confidence)
   Evidence:
   - Exact timing mismatch between sync snapshot apply and async event queuing
   - renderBoardDiff() called before playback events available
   - _hasPendingMoveSourceAtForDiff() explicitly checks queue which is empty
   - Tests would pass if playback events were accessible to diff-renderer
   - Only affects network mode where snapshot is pre-applied

2. **DUPLICATE DOM WRITERS** (SECONDARY - 60% confidence)
   Evidence:
   - Two independent systems updating same DOM cells
   - No coordination between AnimationEngine and DiffRenderer
   - No transactional updates or event ordering guarantees
   - AnimationEngine hides disc, DiffRenderer applies destroy-fade
   - But this is architectural, not a bug per se

3. **UPPERCASE/LOWERCASE MISMATCH** (RULED OUT - 5% confidence)
   Evidence:
   - _getTargetCause() → .toUpperCase() at line 158
   - _getTargetReason() → .toLowerCase() at line 162
   - Hyperactive detection uses .indexOf('hyperactive') >= 0 at line 1924
   - Tests pass with lowercase reason field ✓
   - No case sensitivity issues found

4. **STALE SOURCE EVENTS** (SECONDARY - 70% confidence)
   Evidence:
   - _collectPendingMoveSourceKeysForDiff() reads async queue
   - Queue may be empty, processing, or complete
   - Cache "pendingMoveSourceKeysThisRender" doesn't guarantee accuracy
   - But this is symptom, not root cause

================================================================
SUMMARY & FINAL DETERMINATION
================================================================

PRIMARY CAUSE: **Snapshot replay timing race condition**

The core issue is:
- Network snapshot synchronously applies board state (making source EMPTY)
- diff-renderer is called synchronously BEFORE playback events are queued
- diff-renderer cannot find move source in presentation queue
- diff-renderer falls back to destroy-fade animation
- Later, animation engine correctly animates move
- Result: Two simultaneous animations (destroy-fade + move) = split appearance

The fix must ensure that:
1. diff-renderer knows about move sources even during initial sync
2. diff-renderer skips destroy-fade for hyperactive move sources
3. OR playback events are queued before diff-renderer is called
4. OR diff-renderer checks hyperactive state marker correctly

Current code at line 1604 tries:
`javascript
if (_hasPendingMoveSourceAtForDiff(row, col) || _hasHyperactiveLikeStateForDiff(prevState))
`

But _hasHyperactiveLikeStateForDiff(prevState) may not detect correctly because:
- prevState.special might not have marker (marker added to cardState, not gameState)
- prevState.inherited might not align with snapshot timing
- Hyperactive stone marker state may differ between versions

Solution: Pass move source information explicitly through snapshot or coordinate
playback event queuing to happen before diff-renderer is called.
