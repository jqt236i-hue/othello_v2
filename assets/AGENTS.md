# assets/ AGENTS.md

Asset source, quality, provenance, generation, and delivery boundary. Use this file with the root `AGENTS.md` and any closer nested instruction file.

## SOURCE AND GENERATED OUTPUTS

- Treat player-visible asset identity, timing, and use as part of the applicable `01-rulebook.md` and `正本/` contract. Asset files do not define gameplay behavior by themselves.
- `assets/asset-manifest.json` is generated by `npm run generate:asset-manifest`; do not hand-edit it. Generate optimized fonts, backgrounds, and UI images through the owning `scripts/assets/*` command instead of patching generated outputs.
- Do not source-edit `worker-public/assets/`, built bundles, caches, or temporary conversion output. Change the root source asset or generator, then regenerate the required surfaces.
- Keep intermediate models, checkpoints, candidate generations, and temporary conversion files outside the shipping asset tree. Add only intentionally selected runtime assets and required durable source material.

## PROVENANCE AND RIGHTS

- For every newly added or replaced asset, preserve a durable repository record of its source or creator, license or usage permission, original location, and material edits. For generated assets, also record the tool or model, prompt or input description, relevant settings, and selection or post-processing steps.
- Store provenance in an existing asset-specific design/reference document when one exists. Otherwise create or extend a dedicated repository provenance record; do not leave the only record in chat, a temporary directory, or local tool history.
- Do not copy an asset from another repository merely because it is locally accessible. Confirm that copying and redistribution are allowed, and keep the source repository read-only unless the user explicitly scopes work there.
- Never place secrets, private credentials, or private user data in prompts, asset metadata, filenames, or committed provenance records.

## QUALITY

- Preserve a lossless master for newly generated or materially edited audio when practical, preferably at 48 kHz or higher, and record its durable location if it is intentionally kept outside the shipping tree. Do not describe simple upsampling as a quality improvement.
- Apply trimming, fades, level changes, EQ, denoising, and other edits from the lossless master where available. Avoid clipping, repeated lossy generations, unintended clicks, cut-off attacks or tails, excessive limiting, phase problems, and audible loop gaps.
- Choose mono or stereo according to gameplay use; more channels or a larger file are not automatically higher quality. Produce the browser delivery format once from the best available master and verify that compression did not damage the intended cue.
- For images and fonts, preserve required alpha, dimensions, color behavior, readability, and scaling. Do not enlarge a low-resolution source and call it a higher-quality master.
- When generative creation or subjective visual/audio design is involved, generate and compare multiple candidates and select against the in-game purpose rather than accepting the first technically valid output. Deterministic transformations from an already approved source do not require artificial variants.

## INTEGRATION AND VERIFICATION

- Keep the asset file, logical key, catalog or visual map, preload/runtime lookup, generated manifest, and tests synchronized. Reuse existing asset-key and fallback helpers instead of adding a parallel lookup table.
- For audio, verify the actual trigger, volume balance, latency, overlap or deduplication, mute behavior, interruption, reset, and repeated playback as relevant. A file that plays in isolation is not sufficient evidence.
- For images and fonts, inspect the real browser surface at the relevant viewport and board backend. Check loading failures, dimensions, transparency, cropping, contrast, and fallback behavior as applicable.
- Start with the smallest relevant focused test or asset check. Use `npm run check:asset-case`, `npm run assets:optimized:check`, `npm run match:asset-delivery-smoke:vite`, or browser verification in proportion to the affected delivery path; do not run every asset check for an unrelated one-file change.
- After root asset changes that affect browser-visible output, follow the root `AGENTS.md` rule for `npm run build:browser`. Regenerate the Worker mirror only when the changed surface requires it.
