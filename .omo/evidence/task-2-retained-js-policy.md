# Retained JavaScript Policy

- Date: 2026-04-30
- Scope: TypeScript migration policy for retained `.js` files and `@ts-nocheck` use in the card othello repository.
- Authority: every retained `.js` file must be classified by this policy before a deletion, wrapper replacement, or mirror-generation decision is made.
- Excluded generated/mirror directories for source classification: `dist/`, `worker-public/`, `node_modules/`, `coverage/`, `.git/`, `.venv/`, `.vscode/`.

## Final Goal

- Zero unclassified source `.js` files.
- Zero unclassified `.js/.ts` twins outside generated or excluded directories.
- Generated output may exist only when its generator, owner area, verification command, and removal condition are documented.
- Browser classic scripts must not be pointed blindly at CommonJS `dist/`. Root CommonJS wrappers are Node/test adapters unless separately proven browser-safe; browser script-tag payloads must come from browser-classic artifacts or the prepared `worker-public/` mirror.

## Classification Requirements

Every retained `.js` file must have exactly one category from the seven categories below. Each classification record must include `reason`, `owner area`, `verification command`, and `removal condition`. Do not use a catch-all category when the real owner or runtime contract is unknown; such files remain unclassified and block deletion decisions.

## Categories

### 1. browser-classic-artifact

- reason: Hand-authored or prepared browser script loaded by `<script>` without ESM import syntax and without Node-only globals such as `module`, `exports`, `require`, `__dirname`, or `process` in the browser path.
- owner area: UI/runtime owner for `ui/`, `game/`, `shared/`, `cards/`, or the top-level browser entrypoint that loads the script.
- verification command: `npm run serve` plus a browser boot smoke against the served page; for direct checks, inspect `index.html` or `worker-public/index.html` script order and confirm the script is browser-safe.
- removal condition: remove or reclassify when the browser entrypoint is converted to ESM, bundled, or no longer loads the file as a classic script.

### 2. node-cli-adapter

- reason: A `.js` file exists so package scripts or direct Node commands can execute a TypeScript-migrated CLI through the CommonJS runtime contract.
- owner area: `scripts/` owner or the package script owner named in `package.json`.
- verification command: run the exact Node command from `package.json`, for example `node scripts/serve-with-fallback.js --help`, and any targeted CLI smoke for that command.
- removal condition: remove when `package.json` points to a compiled artifact, a TypeScript-aware runner, or an ESM/CJS entrypoint that executes directly without the adapter.

### 3. node-compat-adapter

- reason: A `.js` file exists only to preserve CommonJS `require(...)` compatibility for tests, Node helpers, or older internal imports after the source moved to `.ts`.
- owner area: source module owner for the matching `.ts` file and the test/helper owner that still imports the `.js` path.
- verification command: `npm run test:jest -- --runTestsByPath <targeted test files>` or `npm run checkall` when the import surface is broad.
- removal condition: remove when all consumers import the TypeScript source, compiled output, or a canonical package/export path instead of the adapter.

### 4. worker-esm-bridge

- reason: A `.js` or `.mjs` bridge exists to satisfy Cloudflare Worker ESM export requirements while adapting CommonJS build output or prepared assets.
- owner area: `workers/` and `worker-public/` deployment owner.
- verification command: `npm run worker:prepare` and `npx wrangler deploy --dry-run`; for local contract checks, dynamically import `workers/match-worker.mjs` and assert `default` plus `MatchRoomDurableObject` exports exist.
- removal condition: remove when the Worker build emits native ESM with statically visible named exports and no CommonJS adaptation is needed.

### 5. generated-output

- reason: A `.js` file is generated by a documented script or compiler and is not edited as source of truth.
- owner area: generator owner, such as `scripts/prepare-worker-assets.ts`, `scripts/generate-catalog.js`, `scripts/generate-observation-gacha-catalog.js`, or TypeScript build ownership for `dist/`.
- verification command: run the generator or build command that owns the file, for example `npm run build:ts`, `npm run worker:prepare`, `npm run generate:catalog`, `npm run generate:observation-gacha-catalog`, or `npm run generate:gacha-hand-catalog`.
- removal condition: remove when the generator no longer emits the file, the generated artifact is replaced by TypeScript source, or the consuming runtime no longer requires checked-in generated JavaScript.

### 6. test-fixture

- reason: A `.js` file is retained only because a test intentionally exercises JavaScript loading, CommonJS interop, browser fixture behavior, or migration parity.
- owner area: `test/`, `tests/`, or the test suite owner that references the fixture.
- verification command: `npm run test:jest -- --runTestsByPath <fixture owner test>` or the named test command documented beside the fixture.
- removal condition: remove when the test no longer needs JavaScript as input, the fixture is replaced by inline data, or the tested compatibility path is retired.

### 7. documented-exception

- reason: A specific retained `.js` file does not fit the other six categories but has an explicit migration note, risk owner, and time-bound or condition-bound exit plan.
- owner area: named owner area in the exception record; broad repository ownership is not enough.
- verification command: the exception record must name the exact command that proves the retained file still behaves correctly.
- removal condition: the exception record must name the concrete event that removes the exception, such as a tracked migration phase completing or a specific consumer being converted.

## `@ts-nocheck` Budget

- Max allowed count: 286 files.
- Initial count command: `Get-ChildItem -Recurse -File -Include *.ts,*.tsx,*.js,*.jsx | Where-Object { path excludes node_modules and .git } | Select-String -Pattern '@ts-nocheck' | Select-Object -ExpandProperty Path -Unique`.
- Budget rule: no new `@ts-nocheck` may be added unless the file is added to this budget with a reason, owner area, verification command, and removal condition.
- Reduction rule: when a file removes `@ts-nocheck`, the max allowed count must be lowered in the same migration evidence update. The budget must never be raised without a documented exception review.
- Removal timeline/condition: remove `@ts-nocheck` from each source area as its public API types, imports, and runtime contracts are migrated; generated files may keep it only while their generator emits it and the generated-output classification remains valid.

## Classification Workflow

- Before deleting any `.js` twin, classify it under one of the seven categories and record the owner and verification command in the migration evidence for that deletion batch.
- Before retaining any source `.js`, prove it is not generated/excluded and record why TypeScript source alone cannot replace it yet.
- Before changing browser script paths, verify the target is browser-safe; never replace browser classic scripts with blind references to CommonJS `dist/` output.
- Before accepting any new `.js/.ts` twin, document which category owns the `.js` file and when the twin will be removed.
- Before accepting any new `@ts-nocheck`, add a budget entry; otherwise the change is not approved by this policy.
