# Lv13 CPU を人間相手に強くするための調査・提案

- 役割: 採用候補を比較するための調査資料。実装計画や確定した製品仕様ではない。
- 状態: 調査完了・提案は未実装。調査日・文書化日ともに 2026-10-07。
- 対象: `lv13-stable-6144`、最大 6,144 遷移・4,700ms、安定石の重み `1.18 / -0.44`。
- 正本: ゲーム仕様は [01-rulebook.md](../01-rulebook.md) §14.11・§14.12、探索設定は [cpu-lv13-search.ts](../game/ai/cpu-lv13-search.ts) の `LV13_SEARCH_CONFIG`。既存の試行結果は [開発・評価記録](cpu-lv13-development-plan.md) を参照する。
- 対象外: 実装、重みの機械学習、自己対局から学習・採用を繰り返すループ、相手のデッキ内容・手札の推定強化、長時間の新規対局、ゲームのビルド・配信変更。

## 結論と優先順位

優先するのは、**①カードを使わない比較基準を残す、②辺の形と崩れやすさを評価する、③特殊石が実際に働く条件とタイミングを評価する**、の３つ。探索量を増やすより、現在の探索が比較する内容を改善する方向を勧める。

**人間相手の強さへの効果は、以下すべて未実証。** コード上の問題を確認できた案と、改善仮説を区別する。工数は実装と関連単体検証の目安で、対局待ち時間は別。

| 優先順位 | 採用候補 | 工数 |
| --- | --- | --- |
| 1 | 「使わずに置く」基準手を探索の最後まで残す | 1〜2日 |
| 2 | 辺の並び・割り込み・安定石の崩れ方を評価する | 3〜5日 |
| 3 | 特殊石・手札の価値を、働く条件と残り時間で評価する | 3〜5日 |
| 4 | 既存の不利世界を、局面に効く攻撃で構成する | 2〜4日 |
| 5 | 適用条件を絞った終盤完全読み | 5〜8日 |
| 6 | 重要度に応じた時間配分と、手番内の予算共有 | 2〜4日 |
| 7 | 仮想世界ごとの「都合のよい未来の判断」を減らす | 5〜10日 |

調査開始時、依頼文に一致する最新版は同じ repo の「カドリバ調整」フォルダーにあった。調査中に別作業で安定石評価が採用され、最終確認時点は上記の版になった。文書化時には本体にもその版が取り込まれているため、ソースへのリンクは repo 相対パスとした。

安定石の最新比較は、重み `1.18 / -0.44` が 128 局で 68勝59敗1分、強めの `2.5 / -1.5` が 66勝62敗。強さの上積みは検出できる大きさではないと開発記録にある。安定石を追加・増量するだけの案は再提案しない。

## 前提: 相手のデッキを伏せた検証条件にする

ローカル実験用の `harness/game.js`（末尾の保存先を参照）は両者の固有デッキを探索へ渡している。人間相手を目標にする比較では、**探索には自分の固有デッキだけを渡し、相手側の `publicRecipes` を省略する**条件を標準にすべき。

通常画面にも、両席の保存済み CPU 選択値からデッキを取得する経路がある。人間席の保存値によって CPU 用デッキを事前分布にしてしまう可能性があるため、席の操作主体によるガードが必要。人間の実デッキが漏れていると確認したわけではない。

- 対戦時の入口: [cpu-turn-handler.ts](../game/cpu-turn-handler.ts#L2279) の `getPublicRecipes`。
- 固有デッキの取得: [cpu-opponent-startup-options.ts](../shared/cpu-opponent-startup-options.ts#L60) の `getCpuOpponentDeckCardIds`。
- 相手側の指定がない場合の分布: [cpu-lv13-scenarios.ts](../game/ai/cpu-lv13-scenarios.ts#L113) の `sampleIndependentPosition`。

この検証条件の修正は、相手の手札読みに労力を割く提案ではなく、依頼された情報制約を揃えるための前提整備。

## 1. 「使わずに置く」基準手を、探索の最後まで残す

### 概要

採用済みのためらい補正を、常に比較相手がある状態で働かせる。補正値の再調整ではなく、比較の成立を保証する修正。

### 根拠

`searchLv13Scoped` は即時評価で根を６候補、浅い応手評価で深読みを３候補に絞る。その後、残った候補にカードを使わない手がある場合だけ `cardUseMargin` を掛ける。通常配置が途中で全滅すると、ためらい補正が消える。

- [cpu-lv13-search.ts: 根の候補選別](../game/ai/cpu-lv13-search.ts#L346)
- [cpu-lv13-search.ts: 深読み候補の選別](../game/ai/cpu-lv13-search.ts#L525)
- [cpu-lv13-search.ts: 補正の条件](../game/ai/cpu-lv13-search.ts#L575)

実例も確認できた。`SP1-selfplay-lv13/g005-s960036-white.steps.ndjson` の判断 index 28、白15手番には通常配置が９手あるが、最新版でも比較候補６枠すべてがカードだった。相手デッキを伏せ、通常の時間制限で再実行しても再現し、約4.704秒で返った。選んだ「盤面縮小神」が悪手だと証明したわけではないが、**見送りとの比較が欠けることは確認済み**。

### すぐ実装する範囲

1. カード使用・手札破壊を含まない完成手番を「見送り基準」として保持する。
2. 根６枠と深読み３枠のそれぞれ１枠を、その基準に予約する。
3. 基準とカード案を同じ世界・同じ深さで比較する。`destroy→use` の計画を「カードを使わない案」と扱わない。

対象選択中など、既にカード使用が確定している状態には、この予約を適用しない。既存の `compareLv13Scenarios`・`commonLv13DepthValues` による比較条件の一致を維持し、総候補数・遷移上限は増やさない。

### 期待効果

人間が通常配置で待っているところへ、CPU が資源を使って局面を悪化させる判断を減らせる。

### 実装コスト

1〜2日。主な変更先は `cpu-lv13-search.ts` の候補保持と最終比較。回帰テストは既存の `test/cpu.lv13-card-margin.test.ts` に近い範囲。

### 検証方法

基準手の脱落、基準手より良い救済カード、合法配置がなくパスと比較する局面を固定テストにする。時間切れ時にも比較する世界・深さが揃うことを確認する。

### リスク

カード候補に使える枠が１つ減るため、強いカード案を落とす可能性がある。総候補数を増やさないので、探索幅の拡大による５秒超過は避けられるが、基準手の応手を完成させるための予算配分は実時間で確認する必要がある。

## 2. 辺の「石数」より、並びと崩れ方を評価する

### 概要

角につながる辺、両端が空いた辺、敵石を挟む辺、割り込み可能な空白を区別する、学習なしの形評価を追加する。

### 根拠

`extractLv13ValueFeatures` は既に角から連続する同色列を加点している。しかし辺全体の並びや、どの支点を失うと何個崩れるかは表していない。

`countLv13StableStones` は通常配置に対する安定性を数えるが、破壊・移動・奪取は探索任せで、拡張も安定判定には考慮しない。

- [cpu-lv13-evaluation.ts: geometry](../game/ai/cpu-lv13-evaluation.ts#L193)
- [cpu-lv13-evaluation.ts: countLv13StableStones](../game/ai/cpu-lv13-evaluation.ts#L103)
- [cpu-lv13-model.ts: 安定石の採用重み](../game/ai/cpu-lv13-model.ts#L52)

最終合算は線形だが、特徴抽出には既に平方根や終盤度、安定石の固定点計算など非線形な処理がある。改善は機械学習モデルの導入ではなく、組み合わせに意味のある特徴を設計することで行える。

### すぐ実装する範囲

1. 盤面形状から実際の辺の連続区間を抽出し、上記４種類の形に分類する。
2. 安定石について、角などの支点に依存する石と、満杯の列を根拠に安定扱いされた石を区別する。公開済みの攻撃や穴の再生成で崩れる部分だけ割り引く。
3. 危険マスの罰点は「実際に相手の角取得につながる形」で掛け、角の隣という座標だけでは掛けない。

新しい純粋 helper の候補名は `extractLv13EdgePatterns`。固定の 8x8 座標ではなく、既存の board view・topology から区間を取得する。未対応の形では現行評価へ戻す。

これは geometry の倍率変更とは異なり、**同じ辺の石数でも意味が違う形を識別する**案。安定石を追加・増量するだけの案は、既存試験と重なるため勧めない。

### パリティ・奇数領域の扱い

初版では終盤の着手順序付けに限定する。空白の連結領域、両者の進入可能性、手番、持ち石を使い、追加配置・時間停止・盤面変更などが効く局面では強く信用しない。

通常リバーシの終盤でパリティを着手順序に使う実例は [Edax の終盤探索](https://github.com/abulmo/edax-reversi/blob/master/src/endgame.c) にある。カードリバーシへそのまま適用できるという根拠ではない。

### 期待効果

人間が作る辺の罠や、長い辺を最後にまとめて反転する狙いに強くなる。危険マスを一律に避けず、安全に置ける例外も扱える。

### 実装コスト

3〜5日。辺の分類と安定石の根拠分類、穴・縮小・拡張のテストを含む。

### 検証方法

石差や辺の石数が近くても、相手が割り込める形と割り込めない形を対にした問題を作る。穴、縮小、拡張後の形も含める。現行評価による深い読みだけを正解にせず、正本の合法な応手で形の差を確認する。

### リスク

通常リバーシの形を過信すると、カードで簡単に崩される。形評価が既存の geometry・安定石と二重加点になる危険もある。全評価地点での区間走査は時間を増やすため、形状部分を topology ごとにキャッシュし、実時間を測る。

## 3. 特殊石・手札の価値を「働く条件と時期」で評価する

### 概要

カードの種類だけで持続価値を与えず、対象、発動時期、アンカーの生存、終局までの機会を評価する。

### 根拠

`lv13MarkerPotential` の生産価値は基本的に「種類別定数×残り寿命の平方根」。盤面や攻撃対象を引数に取らない。`lv13CardPotential` も特殊石を仮の寿命５で評価する。手札評価には持ち石補正があるが、対象の有無や発動機会は入らない。

- [cpu-lv13-evaluation.ts: lv13MarkerPotential・lv13CardPotential](../game/ai/cpu-lv13-evaluation.ts#L45)
- [cpu-lv13-evaluation.ts: extractLv13ValueFeatures の手札評価](../game/ai/cpu-lv13-evaluation.ts#L242)

### すぐ実装する範囲

初版は次の３系統に絞る。

1. **固定範囲の攻撃石:** 破壊可能な敵石と、次の発動までに相手が逃がせる石を区別する。破壊龍の正本処理は隣接敵石を対象にするため、寿命だけでは価値を表せない。[destroy_dragon.ts: processAnchor](../game/logic/cards/destroy_dragon.ts#L296) を根拠とし、対象条件を別ルールとして複製しない。
2. **保護石:** 守る石の継続価値と、実際に防げる攻撃を組み合わせる。既に通常配置では安定した石に保護を足す場合と、重要な生産石を守る場合を区別する。
3. **資源札・遅延札:** 布石上限、将来の支払い、発動前の終局を考慮する。宝箱も手札循環に役立つ場合があるため、種類による禁止にはしない。

究極反転龍のように移動する石は、現在の周囲だけでは評価できない。合法な移動先の分布を使う必要がある。[dragon.ts: processDragonEffectsAtTurnStartAnchor](../game/logic/effects/dragon.ts#L403) の処理と一致させる。

使用時の即時効果は正本の遷移で既に反映されているため、継続価値に二重計上しない。現在対象がない札も、将来の対象や用途がある場合は価値をゼロにしない。

### 使用後の反撃は現在も読んでいる

`prepareScenario` は相手の完成手番と、その後の開始処理まで進め、`deepenScenario` は自分の返し手も読む。問題は反撃が全くないことではなく、候補が途中で落ちることと、読みを打ち切った地点の持続価値が粗いこと。

- [cpu-lv13-search.ts: prepareScenario](../game/ai/cpu-lv13-search.ts#L390)
- [cpu-lv13-search.ts: deepenScenario](../game/ai/cpu-lv13-search.ts#L447)

「今使う」と「取っておく」の比較は、提案１の基準手を残したうえで、同じ深さの相手応手・自分の返し手まで行う。読みを一律に深くする提案ではない。

### 期待効果

人間が攻撃範囲を避けたり、アンカーを狙ったりしたときの無駄打ちを減らす。終盤に働く時間のないカードを出す癖と、今だけ有効な札の抱え落ちを扱える。

### 実装コスト

最初の３系統で3〜5日。全カードへの展開は別段階。

### 検証方法

同じカードで「今使う／次に使う」の優劣が逆転する対局面を作り、相手の反撃後まで比較する。アンカー消失、破壊保護、残り持ち石、最終配置後に次の開始効果が起きない条件も確認する。

### リスク

現在対象がないだけで将来価値をゼロにすると、布石として置くカードを過小評価する。種類ごとのルールを複製すると仕様ずれが起きる。各評価地点で正本の追加シミュレーションを無制限に行わず、純粋な対象検査を使い、実際の追加遷移は予算に数える。

## 4. 既存の不利世界を、局面に効く攻撃で構成する

- **概要:** 世界数を増やさず、不利世界を「強い札の寄せ集め」から「この盤面の弱点に効く合法な攻撃」へ変える。
- **根拠:** 不利世界は既にある。自石10個以下では二連投石・究極破壊神・超引力を優先して埋め、それ以外はカードの一般的な強さで抽選する。実際にどの攻撃が辺や生産石を崩すかは選択基準にない。[cpu-lv13-scenarios.ts: createLv13ScenarioSampler](../game/ai/cpu-lv13-scenarios.ts#L47)
- **期待効果:** 人間が狙う「角の支点を壊す」「重要な特殊石を奪う」「少数の自石を連続配置で消す」攻撃への備えになる。
- **実装コスト:** 2〜4日。
- **検証方法:** 公開手札は保持し、手札枚数・布石・使用条件に反する世界を作らないことを検査。３種類程度の攻撃を固定した局面で、防御手の選択を確認する。
- **リスク:** 毎回最悪の札を仮定すると過度に消極的になる。まず通常２世界＋不利１世界と、既存の平均85%・最低値15%の集約を維持する。代表攻撃の選別に使う遷移も予算に数え、探索時間を測る。

攻撃の試算も正本の `apply/start` を通す。相手の所有カードを推定する処理は加えない。最悪世界の導入そのものや、世界数・探索本数の拡大を再提案するものではない。

## 5. 完全読みは、終盤の適用条件を絞る

- **概要:** まずカード・生成・形状変更・未知のドローが介入しない終盤だけ、全合法手を読む経路を設ける。
- **根拠:** 現在の `tail` は後続候補を原則１本に絞るため、終盤でも完全読みではない。既存 `EndgameSolver` は時間制限がなく、状態キーも盤面・布石・手番が中心で、カード状態を十分に区別しない。枝刈り結果の上限／下限の区別もなく、そのまま接続するのは勧めない。[cpu-lv13-search.ts: tail](../game/ai/cpu-lv13-search.ts#L367)、[endgame-solver.ts: EndgameSolver](../game/ai/endgame-solver.ts#L29)
- **期待効果:** 人間が終盤の偶奇やパスを使って逆転する局面を取り切れる。
- **実装コスト:** 5〜8日。
- **検証方法:** 小盤面・少数空白を全列挙する参照解と照合し、持ち石切れ、連続パス、同じ側の追加行動を含める。
- **リスク:** カード込みでは空白が増え、配置なしの手番もあるため、残り空白数は読み切りまでの上限ではない。分岐数によって５秒超過の可能性が大きく変わる。

初期目安は残り配置機会６程度とし、αβ探索、パリティによる順序付け、正確な状態キーと枝刈り境界を使う。ただし６以下でも５秒以内を保証できるとは未確認。中断時には、途中の値を完全読みの結果として使わず、完了した比較へ戻す。

**未知の相手手札・未来のドローを含む実対局を、５秒で一般的に完全読みする案は勧めない。** 各仮想世界を読み切っても、その世界を仮定した条件付き結果。

今回集計した24局では、通常判断の1,135地点中「両者の手札が空で、盤上マーカーもない」地点は０だった。適用頻度は低い可能性がある。この集計条件だけでも完全読みの適用条件としては不十分で、将来のドローや再シャッフルも確認する必要がある。

## 6. 重要度に応じた時間配分と、手番内の予算共有

- **概要:** 静かな局面を早く返し、危険な分岐では４位の追加深読みより、基準手と有力手の応手比較を先に完成させる。
- **根拠:** 現在は手番完成に40%、浅い比較に残予算の30%など、段階ごとの固定配分が中心。また `runLv10Turn` は助言を１操作ずつ取得し、返された `continuation` を使わない。カード→対象→配置で探索が複数回起こり得る。[cpu-lv13-search.ts: 予算配分](../game/ai/cpu-lv13-search.ts#L324)、[cpu-lv10-turn.ts: runLv10Turn](../game/cpu-lv10-turn.ts#L30)
- **期待効果:** 人間の罠に対する必要な比較を、時間切れで欠かしにくくする。連続した操作の待ち時間も減らせる。
- **実装コスト:** 2〜4日。
- **検証方法:** 同じ観測・注入時計での再現性、短い締切でも合法手を返すこと、操作ごとと手番合計の所要時間を測る。
- **リスク:** 序盤でも強いカードが使えるため、手番番号だけで短縮すると弱くなる。前半で節約した時間を後半の５秒超過に使うことはできない。時間切れは高コストな処理の開始前に確認する必要がある。

重要度には、候補間の差、世界間の順位変動、角や生産石への即時攻撃、少数石・持ち石切れを使う。継続案を再利用するなら、公開状態の一致と通常の合法性検査が必須。

現在の4,700msは探索１回の上限。プレイヤーが感じる１手番全体の待ち時間は、複数の助言要求・転送・演出を分けて測る。

## 7. 仮想世界ごとの「都合のよい未来の判断」を減らす

- **概要:** 公開情報が同じなら、将来の自分の判断も世界間でそろえる。
- **根拠:** `deepenScenario` は世界ごとに自分の返し手を選び、その状態には仮の相手手札が入っている。実際には見えない違いを知ったつもりで将来の手を選ぶ、楽観性が入り得る。これは隠れた実情報の漏洩とは別の問題。[cpu-lv13-search.ts: deepenScenario](../game/ai/cpu-lv13-search.ts#L447)。決定化探索のこの弱点は [ISMCTS の原論文](https://eprints.whiterose.ac.uk/id/eprint/75048/1/CowlingPowleyWhitehouse2012.pdf) でも論じられている。
- **期待効果:** 人間の未公開札に対し、「後で適切に対応できる」と過信する判断を減らす可能性がある。
- **実装コスト:** 5〜10日。
- **検証方法:** 公開観測と自分の手札が同じで、仮の相手手札だけが異なる状態を作り、自分の返し手が公開情報に基づいて選ばれるか確認する。
- **リスク:** 公開観測によるグループ化と共同比較は高コスト。現行探索でどの程度悪影響が出ているか未測定で、５秒以内の計算量への影響も不確か。全面的な探索方式の置き換えは後回しにする。

## 人間相手に特有の弱点について分かった範囲

今回読めた journal は CPU 同士の記録。**「同じ罠に繰り返し掛かった」という人間戦の実例は確認できなかった。**

拒否記憶は不合法操作・取消しの再試行を防ぐもので、合法だが悪い戦術を避ける記憶ではない。[cpu-lv10-turn.ts](../game/cpu-lv10-turn.ts#L30) の `runLv10Turn` と `rejectedActions` が根拠。同じ罠への対策は、相手の手札推定や乱数追加ではなく、提案２・３の形と使いどころの規則へ反映する方向が合う。

## 検証の進め方

1. **独立した局面問題を先に使う。** 辺の罠、アンカー狙い、カードを今使う／温存する問題を、正本の遷移で確認する。現行評価による深い読みは、評価変更の正解にはしない。
2. **相手デッキを伏せた512遷移・128局で退行を確認する。** ユーザー提示の目安は約40分。勝率に加えて、無駄な使用、資源の抱え落ち、危険応手の見落としを集計する。学習や重みの当てはめには使わない。
3. **有望な固定案だけ実時間で確認する。** 代表局面と Worker の時間検査を先に行い、その後必要なら32局・約２時間半の対局へ進む。固定遷移数での再解析時間を、本番の５秒制限の証拠にしない。
4. **人間戦で最後に確認する。** 同じ戦術を繰り返された場合の失敗率と、新しい戦術への対応を重視する。人間を模した固定方針との対局も補助になるが、人間戦の証明にはしない。

人間を模した固定方針の候補は「角と連続辺を狙う」「相手の公開された重要アンカーを狙う」「カードを温存し、CPU の使用直後に反撃する」。各方針も正規の公開情報と自分の手札だけを使い、探索に相手のデッキを渡さない。
