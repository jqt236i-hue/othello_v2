# 人間向け開発ガイド

AI エージェント用 (`AGENTS.md`) とは別に、**人間 (= あなた) が repo の判断軸を持つためのガイド**。
AI の挙動を予測して制御すること、意思決定の質を高めることが目的。

## 役割と非ゴール

- **対象**: 非技術スタートで 2026-01 から AI コーディングで othello_v2 を個人開発中のユーザー
- **正本**: `AGENTS.md` (AI 用契約) / `docs/architecture-contracts.md` (内部構造) / `01-rulebook.md` (ゲーム仕様)
- **非ゴール**: ゲームの仕様そのものの解説、新カードの設計ルール (それらは `01-rulebook.md` / `正本/`)

## どこに何が置いてあるか (意思決定に必要な粒度だけ)

### 触っていい正本

- `01-rulebook.md` — ゲーム仕様 / カード仕様 / UI 表示仕様の**正本**。新カードの挙動を考える時の根拠。
- `正本/*.md` — 既存カード・ターン処理・表示・音の挙動詳細。既存カードの挙動が変わる時だけ更新。
- `docs/architecture-contracts.md` — 内部構造 (層境界・責務分担) の正本。
- `docs/HUMAN-DEV-GUIDE.md` (このファイル) — あなたの運用の正本。

### 触ってはいけない自動生成物

- `worker-public/` — Cloudflare にデプロイされる**コピー**。`npm run worker:dev` / `npm run worker:deploy` が自動同期する。
- `dist/`, `public/module-registry.js` — ビルド・スクリプト生成物。

### 触る必要はほぼない AI 専用領域

- `AGENTS.md` — AI が読む契約。あなたが直接書くことはほぼない (AI の挙動を変える時だけ)。
- `docs/AGENTS.md` — `docs/` 配下のドキュメント管理ルール。
- `test/`, `tests/`, `training/`, `scripts/`, `workers/`, `utils/`, `shared/`, `constants/` — テスト・学習・ビルド・サーバー本体。**AI が全部触る領域。** あなたが直接書くことはほぼない。

## 層をまたがないルール (一番重要)

AI が提案してくる実装が**正しい層に置いてあるか**を判断する時の軸。

```
正本 (docs) ─┬─ 01-rulebook.md         (ゲーム仕様)
             ├─ docs/architecture-contracts.md (内部構造)
             └─ 正本/*.md              (カード挙動詳細)

純粋ロジック層 ─ game/, shared/, utils/  (UI に依存しない、ブラウザに依存しない)
                       ↑
ブラウザ層       ─ ui/, cards/, index.html, entry-browser.js
                       ↑
配信層           ─ workers/ (Cloudflare 側)
```

### 絶対やってはいけない越境

- **`game/` や `shared/` がブラウザや音を触る** — AI が「ここで DOM 操作したい」って言い出したら止める
- **`ui/` がゲーム判定をする** — クライアント (= ブラウザ) は表示担当、判定担当じゃない
- **`worker-public/` を直接編集する** — 触ると Cloudflare デプロイとの同期が崩れる
- **正規化や判定処理のコピーを増やす** — 既存の `utils/owner-helpers.ts` 等を使うのが正解、AI に「コピーでいい?」って聞かれたら NO

### AI が出しがちな anti-pattern (はねる時の判断材料)

- 「クライアント (= ブラウザ) の状態を判定根拠にする」
- 「ゲーム層から UI を呼ぶ」
- 「`worker-public/` を直接いじって同期する」
- 「正規化や判定のコピーを各ファイルに置く」

## AI への依頼パターン 3 種類

| 依頼 | AI がやること | あなたがやること |
|---|---|---|
| **機能追加 / 新カード実装** | 仕様確認 → 01-rulebook.md 更新 → 実装 → テスト | 仕様判断・動作確認 |
| **バグ修正** | 原因調査 → 修正案と影響範囲の提示 | 修正 OK 判断・修正後の確認 |
| **リファクタリング** | 調査 (リファクタ箇所を根拠付きで列挙) → 優先順位付け → 計画書 → 実施 | 優先順位の選択・計画レビュー |

### リファクタリング依頼の詳細フロー

1. 「`ui 関連` で断言できるリファクタ箇所ある?」「`カード効果関連` でリファクタ必要?」のように**領域を区切って調査させる**。
2. 根拠付き優先順位リストが返ってくる (例: 「最優先 ○○、次点 ○○ と ○○、まだ不要 ○○」)。
3. あなたが「最優先と次点を全部」と範囲を絞る。
4. AI がリファクタ計画書 (実行手順書) を作成。
5. AI が実施 → コードレビュー → 必要なら最終修正 → 完了。

**意思決定 (何を直すか・何を優先するか・何を捨てるか) はあなた、AI は道具。**

## 意思決定の分担

### AI が勝手に決めていい判断

- ファイル内の細かい実装パターン
- 既存コードとの整合性
- テストの追加・削除
- 内部関数の命名・配置

### あなたが判断すべきこと

- 何を直すか、何を優先するか、何を残すか・捨てるか
- 仕様の細部 (新カードの挙動 / UI の見た目 / 数値バランス)
- 公開範囲・リリース判断
- AI の能力に対する信頼度 (今の自分にこれは重いかを判断する)

### AI に確認質問された時の見分け方

- **答えるべき質問**: 「A と B どちらを採る?」「この仕様で合ってる?」「スコープどこまで?」 → 意思決定が要る
- **「自分で読みに行って」と返していい質問**: 「このファイル分かる?」「このコードどう思う?」 → AI 側に読みに行く責任

## AI との会話で気をつけること

### 重めの作業を AI に振る時

- 最初に「途中で動作確認しながら進めたい」と伝えると、AI が区切りごとに確認を挟むモードで動く。
- 不安な箇所は **都度「ここ大丈夫?」って聞いていい**。AI に対する健全な懐疑は正しい使い方。

### AI から完了報告が来た時

- 動作確認ポイントを確認: テスト結果 / 既存機能への影響 / 画面での挙動
- AI の「完成しました」だけで終わらせない

### AI が「分からない」と言った時

- 今のフェーズ (gpt-5.5 high → Mavis 移行中) では **AI の能力に対する不安が残っている**。だから「自信ない」と言ってきたら軽視せず、追加調査を検討する。

## AI 専用領域への依頼 (1 行まとめ)

- **新カード実装**: 「新カード [名前] 実装して。仕様は [ここに書く]」→ AI が `01-rulebook.md` 更新 + 実装
- **バグ修正**: 「[症状] を直して」→ AI が原因調査から
- **リファクタ調査**: 「[領域] でリファクタ必要箇所ある?」→ 根拠付き優先順位リストが返る
- **リファクタ実施**: 上記で選んだ項目を「[選んだ項目] を直して」→ 計画書が出て、承認で実施
- **docs 整合性**: 「[doc A] と [実装/別 doc] で矛盾してない?」→ 修正案が返る
- **デプロイ動作確認**: 「[機能] を Cloudflare にデプロイして動作確認したい」→ `worker:dev` / `worker:deploy` 経由で実施

## Git との付き合い方 (あなたは Git を触らない)

Git は AI が作業の記録と保険 (GitHub へのバックアップ) のために使う道具で、あなたが操作することはない。覚えることは次の 3 つだけ。

| 言うこと | 起きること |
|---|---|
| (何も言わない) | 作業が終わるたびに AI が記録 (コミット) し、GitHub に上げる。これが既定の動き。 |
| 「本体に取り込んで」 | 別の作業コピー (orca が作る `カドリバ調整` などのフォルダ) で作った変更を、本体 (`F:\Desktop\othello_v2`) に合流させる。 |
| 「今の状態を教えて」 | AI が「対応不要」か「あなたの判断が必要」を先頭に付けて、日本語で説明する。 |

### 聞き返されても困らないために

- 「未コミットの変更が残っています」= まだ記録していない編集があるという意味。**放置しても壊れない。** 気になるなら「全部記録して」と言えば AI が片付ける。
- 「巻き戻し」「履歴の書き換え」は AI に禁止してある。AI がそれを提案してきたら、理由を日本語で説明させてから決める。急ぐ必要はない。
- AI が Git の選択肢 (merge / rebase / reset など) で質問してきたら、「ゲームがどうなるかで説明して。おすすめはどれ?」と返してよい。`AGENTS.md` でそう答えるよう指示してある。

### バックアップと復旧

- バックアップは GitHub (`origin/main`)。作業完了ごとに AI が上げるので、GitHub が最新に近い。
- 2026-10-06 に、本体と GitHub の記録系統がずれていたのを統合した。その時の退避データは `C:\Users\quarr\othello_v2-git-backup\` にあり、手順は `docs/refactor-baselines/history-rewrite-preflight.md` にある。何かあったら AI に「2026-10-06 の退避から戻せる?」と聞けばよい。

### 作業コピー (orca のフォルダ) について

- orca が `C:\Users\quarr\orca\workspaces\othello_v2\<名前>` に作る各フォルダは、本体の別コピー。そこでの作業は AI が終了時に本体へ合流させ、GitHub にも上げる。
- 合流できない時 (本体で別の作業が進行中など) は、AI が「本体への取り込みは未了」と報告する。急ぎでなければ次の作業の時にまとめて取り込ませればよい。
