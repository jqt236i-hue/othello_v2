## 方針と開始条件

優先順位は **探索内部の計測 → 不要なハッシュ計算 → 複製と評価の重複 → 並列数の再選定** とする。まず、同じ公開局面・同じ計算量・同じ判断をより短い時間で処理する。記録形式の作り直しや探索予算の削減を先行させない。

この計画で直ちに開始できるのは、P0の対象確定と保存記録の読取り。CPUを使う性能測定は実行中の比較試験と重ならない時間に、独立して保存した対象で行う。本体側の未完了編集へ同時に書き込まない。既存試験の停止、設定変更、候補への差し替えをこの計画の着手操作に含めない。

最初の依頼は計画作成のみだった。2026-09-14の後続依頼でP0からの実装・実測が明示されたため、以下を実行し、末尾に結果と未達事項を残す。

## 2. 守る条件と速度の評価方法

1. ゲーム状態・PRNG消費・合法性・拒否理由・追加行動・pending・終了結果を維持する。CPUの入力は通常の公開観測のみ。比較器が持つ全状態を探索へ渡さない。
2. 同じ候補の固定計算量比較では、行動、継続候補、評価値、候補順、拒否履歴、遷移数を一致させる。除外できるのは計測時間と追加した性能統計のみ。局面評価の係数、候補削減、探索深さ、探索順変更は高速化と同時に行わない。
3. 本番時間制限の比較では実時計を使う。速くなれば打切り位置や行動が変わり得るため、固定計算量の一致と本番対局の勝率は別に検証する。正式評価だけ時計を止めたり、計算量や時間上限を増減したりしない。
4. 保存Lv10と既存Lv1–10の判断経路は変更しない。Lv11向けの最適化は通常ブラウザと自己対局で同じ実装を呼ぶ。共通helperへ注入点を追加する場合も従来の既定経路を保つ。
5. 実際に適用した全行動、失敗、全ゲーム状態/乱数の照合、停止・再開と重複防止を維持する。比較除外は既存`PRODUCTION_STATE_EXCLUSIONS`から拡大しない。
6. 正式な強さ評価・条件再発行・通常UI採用は[Lv11全体計画](cpu-lv11-execution-chaos-dragon-plan.md)に従う。性能比較は開発条件だけで行い、採用用の未使用条件を消費しない。高速化後は新しい候補ハッシュとして扱う。

性能目標は、P0で固定した候補に対する**同じ計算量の判断時間中央値をまず1.5倍以上高速化**することとする。これは技術目標で、勝率の追加採用条件ではない。入力群全体のP95時間の悪化は5%以内、最大メモリの増加は10%以内を目安に実測し、変動の範囲も添える。未達なら原因と次の改善余地を示して設計を見直し、達成したことにしない。

「遷移/ms」「同じ判断の所要時間」「通常予算での1局時間」「一定数の対局を終える壁時計時間」をそれぞれ報告する。時間上限まで探索する局面では、処理が速くなっても思考時間は同じまま探索量が増える。これを対局時間の短縮と混同しない。

dev1の内訳で、Lv11の探索だけを2倍にでき、判断列と探索量が同じと仮定した場合でも、14局合計は約30.3分から約21.9分への短縮にとどまる。保存Lv10の探索時間は残る。この計算は上限を理解する参考であり、実時計で行動が変わる対局の予測値ではない。

## 4. 実装手順

### P0 — 最適化対象と比較入力を固定する

目的: 本体で進行中の判断改善と、高速化の効果を混ぜない。

- 開始時に適用AGENTS、git statusと関連差分、実行中の実験manifest/所有プロセスを読む。通常8000と他作業のプロセスは操作しない。
- 本体の編集が区切られた候補を1つ選び、そのソース・実行コード・Node・依存・設定・共通ルールを独立コピーして記録する。dev1/dev2や現在のrootを無条件に基準としない。
- 既存の開発journalと[カードfixture](../scripts/production-card-fixtures.ts)から、通常序盤/中盤/終盤、特殊石・遅延効果、盤面拡張/穴/縮小、多段選択、追加配置、運命の意志による操作権変更を含む24公開局面を選ぶ。各区分3局面を原則とし、重複を除いて不足を明示する。
- 判断時点の公開観測、公開デッキ事前情報、除外行動とキャンセル記憶に由来する入力を保存する。色を均等にし、全入力と選定規則を改善結果を見る前にハッシュ固定する。未公開の全状態は回帰比較用の別入力としてのみ保存する。
- 新しい性能入口を`scripts/perf/measure-production-selfplay.ts`、npm名を`perf:production-selfplay`とする案で実装する。現在は存在しない。既存[局面抽出](../scripts/inspect-production-decision.ts)と単局実行を再利用し、固定計算量/本番時間制限/全局の各モード、候補root、入力群、並列数、出力先を明示できるようにする。暗黙にビルドしない。

完了条件: 再実行可能な対象manifestと24入力ができ、双方の候補へ同じ公開入力を渡せる。元試験を変更していない。

### P1 — 費用を分解し、改善対象を確定する

目的: 全体時間の97.7%を占めた探索の、どの処理が重いかを確定する。

- 保存対象だけを読み込む計測用プロセスで、初回ロードとウォームアップ後を分ける。探索、公開観測生成、状態複製、仮想行動/ターン開始、状態ハッシュ、評価、合法手列挙、GC、実際の行動適用、JSON化、fsync/checkpoint、圧縮、起動/終了を測る。
- CPUプロファイルと明示区間計測を併用する。親子処理の包含時間を単純加算せず、排他的な時間と呼出回数を報告する。比較のためのプロファイラは正式対局に入れない。通常時の性能統計追加が必要なら、オフ時の費用も確認する。
- 固定計算量は64遷移と512遷移を全24局面、宣言した本番最大遷移を代表8局面で確認する。このモードの時計省略は正確性・速度比較専用。本番時計の測定は全24局面で別に行う。
- 基準→候補→基準の順で測定し、温度・バックグラウンド負荷の変化を検出する。まず3組、ばらつきが10%を超える場合は負荷原因を調べる。原因の分からないばらつきから速度向上を断定しない。
- 1計測プロセスは最大10分/1536MiB heap、キャンペーンは最初の結果確認まで最大30分。下限の空きメモリ2GiB/ディスク1GiBと停止時の子終了を既存実験管理に合わせて守る。全局再測定の容量は既存journalサイズから先に見積もる。

判断規則: ハッシュ、複製、評価のうち探索時間の10%以上を占める処理をP2/P3の対象にする。どれも該当しなければ関数別上位を調べ直して当該ステップを更新する。記録/起動等がバッチ壁時計の10%未満ならP4では形式や耐久性を変更しない。

完了条件: 基準計測JSONとCPUプロファイル、各費用の割合、最初に変更する処理、その理論上の短縮余地を記録できる。

### P2 — Lv11の仮想遷移で不要な状態ハッシュを作らない

前提: P1でハッシュ計算が10%以上を占め、探索側に返却stateHashの利用者がないことを再確認できた場合。満たさなければP3へ進み、理由を残す。

- 既存`createTurnPipelineModule`を使ったLv11専用のsimulation構成を用意する。CardLogic/Core/ターンフェーズ/BoardOps/合法性・runtime利用可能性検査は同じものを使う。
- factoryの既存`computeStateHash`注入点で、Lv11仮想遷移の返却用ハッシュだけを生成しない。型で許されるnullとして扱い、偽のハッシュを返さない。通常のauthority、ProductionMatch、通信、保存Lv10は既存の完全なハッシュ生成を維持する。
- `applyLv10Action`の処理を複製せず、遷移サービスの省略可能な注入等で同じ行動適用を再利用する。従来呼出しは既存Pipelineを使う。Lv11だけが専用構成を渡す。ブラウザのLv11探索にも同じ構成を接続する。
- ターン処理がPRNG checkpointを保存する動作、失敗分岐、selectionFailed判定、イベントと取消判断はそのままにする。`applyTurn`への直結で安全な行動適用を迂回しない。

検証: 仮想遷移の旧/新をカード代表局面と24入力で比較し、全ゲーム状態・PRNG・イベント・拒否が一致。違いは未使用の返却stateHashだけ。固定計算量の全判断出力が一致し、入力が変更されない。authorityのハッシュ出力とLv10既存テストは維持する。

### P3 — 測定された複製・評価の重複を減らす

前提: P1の内訳と、P2適用時はその再計測結果があること。費用の大きい項目だけ実装する。

- 同一探索状態を再評価する箇所は、1判断内で有効なキャッシュを使う。状態をimmutableとして扱えることを確認し、状態identityと評価するプレイヤーを区別する。ターン開始/行動適用後の状態へ引き継がない。キャッシュはモジュール外や保存状態に持ち出さない。
- 盤面座標・隅・所有者などは既存board kernelを利用して同じ状態内で再利用する。合法手には特殊石、凍結/保護、pending、操作側等も影響する。盤面配置だけをキーにしない。全状態の署名生成が再計算より高価なら採用しない。
- カードIDに対して固定の潜在評価、定数表、近傍オフセット等の生成を外へ移す。現在の係数、値の合計順、比較順、同値時の順序を維持する。
- 複製では、所有者確認など単一値取得のための全snapshotを避ける案と、同一境界のsnapshot再利用を先に検討する。外部へ可変のauthority参照を公開しない。`before`/`after`/checkpointを後続手で書き換えない。
- `structuredClone`とJSON cloneはundefined、疎配列、非有限数、関数等の意味が異なる。機械的置換はしない。専用cloneが必要なら、実データの許容形式と未知フィールドの保存、参照独立性を明示し、既存処理との全状態一致を証明する。汎用deepCloneの一括変更は行わない。

検証: 固定入力24件に加え、同盤面でもpending/マーカー/手札費用/操作側が違う局面で誤った再利用が起きないことを確認。全カード代表回帰、石の復活、拡張・穴、連続選択、拒否後の再判断で状態と判断が一致する。入力・兄弟分岐・過去journalの非破壊、メモリ上限を確認する。

### P4 — 記録とバッチ運用を必要な範囲で改善する

前提: P1のバッチ計測で10%以上の費用がある場合だけ構造変更を検討する。

- 同一境界のJSON化や集計の重複、進捗表示の過剰な更新を先に減らす。全行動journalと判断記憶は省略しない。失敗を完了として扱わない。
- 最初の実装範囲では、毎判断のjournal fsyncとcheckpoint整合性を維持する。書込み間引きや非同期永続化、差分だけの新journal形式は、損失境界と復旧方法を別途設計する必要があり本計画の初期実装から外す。
- 起動/ハッシュ走査が大きい場合も、凍結ファイルの検証を単に省かない。信頼できる同一実行内の再利用範囲と改変検出を設計してから変更する。永続Workerへの置換は計測で費用が確認された場合に限り、対局間の状態/記憶/乱数/キャッシュ漏れを検証する。

完了条件: 通常完了、判断間の停止と再開、記録途中の失敗で旧仕様どおり監査でき、完了件数・行動番号・判断記憶が維持される。構造変更不要なら測定根拠を残してこのステップを終える。

### P5 — 本番時間制限と並列実行で効果を確認する

- P2/P3後の固定計算量比較で§2の目標と一致条件を確認する。性能値を出す実行にはCPUプロファイラを付けない。
- 最適化前後を同じ24入力・本番clock/budgetで比較する。時間中央値/P95/最大、遷移数、遷移/ms、時間打切り率、候補評価数、代替/拒否率、CPU使用とRSSをCPU別に出す。思考上限は変更しない。
- 基準Lv10と候補をそれぞれ同じ入力群で、1→2→1、必要なら1→4→1並列で測る。比較試験と重なる負荷は避け、ホスト・電源設定・他の高負荷プロセスも記録する。
