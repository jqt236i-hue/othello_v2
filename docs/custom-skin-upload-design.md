# カスタムスキン画像読み込み設計

## 文書の役割

この文書は、見た目設定パネルからプレイヤー自身の画像を読み込み、背景・盤面デザイン・通常石スキンとして保存・選択・削除できる機能の実装設計を定める。プレイヤー向けの表示仕様は `01-rulebook.md`、UI内部の責務境界は `docs/architecture-contracts.md` を正本とする。

## 問題と目標

現在の見た目設定は、ソースに登録済みの画像カタログと選択IDを切り替える方式である。公開URL上のプレイヤーが自分の画像を読み込み、保存後も同じブラウザで利用できる仕組みはない。

目標は次の通り。

- `背景`、`盤面デザイン`、`石` の各タブに `画像読み込み`、`保存`、`削除` 操作を追加する。
- 読み込んだ画像を既存のプレビューと実ゲーム表示へ適用する。
- 保存したカスタムスキンを同じブラウザの個人データとして、ページ再読み込み後も復元する。
- 既存カタログ、既存の選択保存、ネット対戦の権威境界を壊さない。

## スコープと非スコープ

### スコープ

- 背景・盤面デザインは画像1枚を登録する。
- 通常石は黒石・白石の画像を1枚ずつ登録する。
- PNG / JPEG / WebP の読み込みとプレビュー。
- 画像名の入力、保存、保存済みカスタムスキンの選択、削除。
- ブラウザの IndexedDB への画像本体保存と、既存 localStorage への選択ID保存。
- 既存の通常スキンとカスタムスキンの同じ一覧内での表示。

### 非スコープ

- アカウント、ログイン、サーバーへの画像アップロード。
- カスタム画像の他端末同期。
- ネット対戦相手へのカスタム画像共有。
- 見た目プリセットコードへの画像バイナリ埋め込み。
- 特殊石・カード画像・盤面フレームのカスタム化。

「公開URLで自分オリジナルのスキンを作る」は、公開されたゲームURLを開いた各プレイヤーが自分のブラウザ内で作成・保存できる意味に限定する。サーバー上の公開ギャラリーやURLによる共有は別設計とする。

## 現在の構造と根拠

- `ui/background-skin/catalog.ts` は背景画像のカタログ、`runtime.ts` は `body` への背景適用を担当する。
- `ui/board-skin/catalog.ts` は盤面下地カタログ、`runtime.ts` は `--board-surface-texture-image` への適用を担当する。
- `ui/stone-skin/catalog.ts` は黒白2画像の通常石カタログ、`runtime.ts` は `--normal-stone-black-image` / `--normal-stone-white-image` へ適用する。
- 各 `controller.ts` はカタログを一覧表示し、選択時に runtime と selection を呼び出す。
- 選択IDは `localStorage` に保存されるが、画像本体を保存する仕組みはない。
- `ui/hand-skin/controller.ts` が3つの見た目タブを組み立てるため、カスタムアップロードUIは各スキンcontrollerの責務として追加し、親controllerには新しい表示責務を持ち込まない。

## 採用設計

### データ保存

`ui/custom-skin/storage.ts` を追加し、IndexedDBデータベース `card-reversi-custom-skins` の `skins` object store に次のレコードを保存する。

```text
{
  id: "custom:background:<uuid>" | "custom:board:<uuid>" | "custom:stone:<uuid>",
  kind: "background" | "board" | "stone",
  label: string,
  backgroundImage?: Blob,
  boardImage?: Blob,
  blackImage?: Blob,
  whiteImage?: Blob,
  createdAt: string,
  updatedAt: string
}
```

読み込み時に Blob から object URL を作成し、既存カタログの `imagePath` / `blackImagePath` / `whiteImagePath` と同じ形へ変換する。object URL はレコードの再読み込み時に破棄し、削除時にも破棄する。選択中IDは既存の各 selection module の localStorageキーへ保存する。

IndexedDBが利用できない場合は保存操作を失敗として表示し、既存スキンは引き続き利用できる。カスタム画像を一時プレビューするだけの object URL と、保存済み画像の object URL を混同しない。

### カタログ統合

背景・盤面・石の各 catalog module は、既存の固定カタログに `custom-skin/storage.ts` のメモリキャッシュを追加して返す。固定カタログの定数や既存のID正規化は変更せず、`custom:` 接頭辞のIDだけを追加で解決する。保存完了・削除完了後は `custom-skins-updated` UIイベントを発火し、各controllerが一覧と選択状態を更新する。

初期起動では固定スキンを即時表示した後、IndexedDBのhydrate完了時にカスタムスキンを一覧へ追加する。保存済みカスタムIDが localStorage に残っている場合は hydrate 後にそのIDを再適用し、無効化・削除済みの場合は既存の既定スキンへフォールバックする。

### UI

各対象タブの一覧先頭にカスタムスキン作成エリアを置く。

- 背景・盤面デザイン: スキン名入力、`画像読み込み`、プレビュー、`保存`、`削除`。
- 石: スキン名入力、`黒石画像` と `白石画像` の読み込み、2枚のプレビュー、`保存`、`削除`。
- 既存スキンを選択した状態で保存すると新しいカスタムスキンを作る。
- カスタムスキンを選択した状態で保存すると、そのカスタムスキンを更新する。
- `削除` はカスタムスキン選択時だけ有効にし、固定スキンは削除できない。
- 画像読み込み直後は未保存のプレビューを表示し、保存成功後に一覧のカスタムカードとして確定する。
- 画像形式・容量エラー、石の片側だけ未指定、IndexedDB保存失敗は作成エリア内の status に表示する。

1つの画像は最大8 MiB、名称は24文字まで、受け付ける MIME type は `image/png`、`image/jpeg`、`image/webp` とする。石は透明背景のPNG / WebPを推奨するが、形式上は同じ画像形式を受け付ける。

### 表示とネットワーク

背景・盤面・石の適用は既存 runtime のCSS変数経路を使う。ゲームロジック、Worker、local server、ネットワークsnapshotにはカスタム画像データを入れない。背景・盤面・通常石は従来仕様どおりローカル見た目として扱い、ネット対戦中も各端末の選択をそれぞれ表示する。

既存の見た目プリセットはIDだけをコード化するため、カスタム画像を含むプリセットコードは今回対象外とする。同じブラウザの保存済みIDであればプリセット適用は動作するが、別ブラウザへコードだけを渡しても画像本体は移らない。

## 代替案

### localStorageへData URLを直接保存

実装は簡単だが、5 MiB前後の容量制限、同期APIによるUI停止、画像数が増えたときの全件読み書きが問題になるため採用しない。

### サーバーへアップロードして公開IDを発行

別端末同期やURL共有には適しているが、認証、容量制限、削除権限、公開画像の不正利用対策、Worker / storage設計が必要になる。今回の「公開URL上で個人用に作成・保存する」要求には過剰であり、将来の別機能として切り離す。

## 互換性・失敗時の扱い

- 固定スキンのIDとファイルパスは変更しない。
- IndexedDBがない環境では固定スキン一覧へフォールバックする。
- 保存済みレコードが壊れている、画像Blobを復元できない、object URLを作れない場合はそのレコードを表示せず、既存スキンを使う。
- 保存操作の二重実行は controller の保存中フラグで防止する。
- object URLは削除・再hydrate時に解放し、ページ内での再選択によるURLの蓄積を防止する。

## 検証方針

- storageのID生成、形式・容量・名称の正規化、削除対象判定をJestで検証する。
- background / board / stone catalogがカスタム定義を解決し、既存runtimeへ画像パスを渡すことをcontrollerテストで検証する。
- DOMテストで各タブに画像読み込み、保存、削除が表示され、固定スキン削除が無効であることを確認する。
- `npm run typecheck`、関連Jest、`npm run build:browser` を実行する。
- ブラウザで公開URL相当のローカル静的サーバーを使い、画像選択、保存、再読み込み、削除を確認する。

## Self-review

- IndexedDBに画像本体を保存することで、localStorage容量超過を避けつつ「個人のデータ」を満たせる。
- カスタム画像をネットワーク権威層へ入れないため、ゲーム状態・相手の表示・Worker mirrorの契約を汚さない。
- background / board / stone の各controllerへUIを置くことで、既存の `catalog → selection → runtime → controller` 境界を維持できる。
- 公開URLから別端末へ共有できる機能は、認証とサーバー保存が必要な別要件であるため、今回の実装完了条件から除外した。

以上の見直しにより、要求された個人用カスタムスキン機能の最小で持続可能な範囲を確定した。
