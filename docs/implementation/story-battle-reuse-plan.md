## 3. 守る条件

1. 正常な現行モードでは、同じ条件・乱数・操作から、盤面、手札・山札順、チャージ、対象選択、石とカードの識別子、手番、勝敗が一致する。
2. 乱数の消費順、ターン開始の適用回数、カード消費、効果解決の順序を維持する。比較のために実際の対戦へ同じ操作を二重適用しない。
3. coreはUI・DOM・音・Steam API・ファイル保存・ネットワーク接続を所有しない。ホストとの接続は明示的に注入する。
4. 盤面のSingle Visual Writerと、現在のPixi／DOM compatibilityの境界を維持する。物語画面や新APIが直接盤面を描き直さない。
5. 勝敗確定と演出完了を区別する。演出完了の失敗・タイムアウトを成功に読み替えて物語へ進めない。
6. 前の戦闘のCPU応答、予約処理、演出完了、音、入力が、終了後や次の戦闘へ反映されない。
7. 中断、失敗、画面破棄を勝敗に変換しない。報酬・物語進行の決定はホスト側が行う。
8. 通信ではサーバーが正本のまま。製品セーブ用の完全状態を公開snapshotやWorkerメッセージへ混入させない。
9. 初期化・復元は一時状態で検証し、成功してから現在の対戦へ反映する。保存失敗でも直前の有効なセーブを維持する。
10. root sourceを編集して既存スクリプトから生成する。生成物・mirrorの手編集で整合性を作らない。

既存仕様の明確な不具合を発見した場合は、挙動維持の変更と切り分ける。仕様から正しい結果が決まるものは回帰テストとともに修正し、製品判断が必要な差は理由と選択肢を記録して該当部分を保留する。独立した作業は続行する。

## 4. 目指す責務とAPI案

以下の名称・配置は設計案であり、既存の公開APIではない。フェーズ0で実際の依存関係を確認して確定する。

| 層 | 所有するもの | 主な配置候補 |
| --- | --- | --- |
| 共通契約 | 戦闘条件、入力、結果、保存形式、検証結果 | `shared/battle/` または既存の契約所有者 |
| 対戦実行 | 正本状態、乱数、既存pipeline呼び出し、合法性、終了判定 | `game/battle/` または既存の実行所有者 |
| 画面接続 | mount、入力接続、CPU実行の接続、演出完了、破棄 | `ui/battle/` と既存bootstrap／render lifecycle |
| 既存ブラウザadapter | 現在の画面設定を戦闘条件へ変換、既存の結果画面 | `ui/bootstrap/`、`ui/handlers/` |
| 保存先adapter | ブラウザ保存、デスクトップ保存、失敗通知 | coreの外。デスクトップ固有部分は新作側 |
| 新作ホスト | 会話、章・進行フラグ、戦闘への遷移、報酬、Steam連携 | 新作リポジトリ |

必要な操作は、対戦生成、合法な操作の適用、状態参照、結果取得、イベント購読、画面接続、停止・破棄、保存用export／restoreである。たとえば `createBattle(config, ports)`、`apply(command)`、`getResult()`、`exportSnapshot()`、`restoreBattle(snapshot, ports)`、`dispose()` のように表せるが、API数やファイル数を増やすこと自体を目標にしない。

対戦状態と画面状態は別に管理する。画面側は概念上 `unmounted → mounting → active → settling → finished → disposed` を持ち、異常・中断の経路も明示する。これはホスト接続の状態であり、カード・ターンの既存状態機械を置き換えない。

- 結果データは正本の終了判定から作り、表示済みフラグやDOM文言から判定しない。
- ローカル対戦で物語へ戻る通常経路は、正本の結果確定と、その対戦の最後の演出完了が両方成立してから通知する。
- 結果IDと戦闘IDを持ち、同じ終了を二度通知しない。保存後の再起動も含む報酬の重複防止は、新作の進行セーブと組み合わせて検証する。
- 状態参照は外部から正本を書き換えられない値で返す。入力と復元データは入口で検証する。
- 初版の画面は同一ホスト内で同時に一戦だけ接続できればよい。重複mountは明示的に拒否し、終了後の再接続を保証する。
- 通常の会話への復帰では戦闘sessionを終了し、再利用するpage runtimeの所有者はホストの寿命まで保持する。戦闘の `dispose` とpage／hostの最終破棄を別契約にする。
- CPUの強さや判断用メモリーをUIの寿命へ暗黙に結び付けない。戦闘継続に必要なものと、その判断だけのキャッシュを分類する。

### P2. 共通対戦APIと既存画面adapter

**作業**

1. 既存のcore、カードruntime、turn pipeline、乱数checkpointを利用する対戦入口を作る。Node用実行クラスを画面へそのまま移植しない。
2. 生成、操作、状態参照、イベント、結果取得を型付けする。ターン開始の責任者を一つにし、最初のドローや効果を二重適用しない。
3. 現在のresetから、条件を作る部分、対戦生成、既存画面の初期化を分ける。既存公開関数は互換adapterとして段階的に接続する。
4. APIの結果にはルール上の拒否、runtime異常、未終了を区別して表す。満盤だけで終了にせず、現在の正本による終了条件を利用する。
5. `ProductionMatch` とブラウザから共通化できる部分は同じ所有者へ寄せる。移行中の比較実装を二つの恒久的なルール実装にしない。
6. 公開の中立な状態・操作型をAI層に依存させない。CPU側は既存の観測・思考・適用経路を維持する。

**検証・完了条件**

- P0の各ケースで、従来経路と新入口の各操作後の正本状態、乱数checkpoint、イベントの意味と順序、拒否理由、勝敗が一致する。
- 拒否された操作の乱数の扱いも現行経路と比較する。`ProductionMatch.apply` は不正操作で盤面を採用しない場合でも消費した乱数を保持するため、「失敗なら全状態を巻き戻す」へ一律変更しない。必須依存不足による変更前拒否とは区別する。
- 比較は独立した状態と乱数で行う。表示用・実行時参照の除外は既存の定義と根拠を確認し、差分隠しの除外を追加しない。
- 実ブラウザの通常開始・reset・カード・着手・CPU引き渡し・結果が維持される。
- sourceだけでなくbuilt Node、Vite/classic、共有部分を使うauthorityでも必要な検証が通る。

### P3. 仮の物語画面との通常終了往復

**作業**

1. 製品の章や素材を使わない最小ホストを作る。「仮の会話 → 設定した戦闘 → 勝ち／負け／引き分け別の仮の会話 → 再戦」を実装する。
2. 画面接続の責任者を一つにする。盤面、手札、対象選択、HUD、音の必要範囲を既存renderer・presentationへ接続する。
3. 正本の終了結果と最後の演出完了を別々に受け取り、同じ戦闘の両方が揃ってからホストへ戻す。固定待ち時間を演出完了の代用にしない。
4. 既存の結果画面・観測石・スコアなどの処理が新作で勝手に発生しないよう、結果consumerと報酬の所有者を明確にする。既存ブラウザ側の結果・報酬は維持する。
5. 物語画面と対戦画面の入力フォーカス、キー操作、音の担当を切り替える。画面を隠しただけの対戦を動かし続けない。

**検証・完了条件**

- 通常入力で一戦を完了し、最終盤面の演出後に対応する会話へ一度だけ戻る。
- 勝ち・負け・引き分け・終了直前の効果を、それぞれ適切なfixtureと操作で検証する。
- 再戦に前の石、手札、選択枠、結果表示、音が残らない。
- 現行の通常配信も同じ最終ソースで正常に遊べる。

### P4. 中断・破棄と非同期処理の終了管理

**作業**

1. 戦闘IDと世代を接続の境界に持たせ、CPU応答・予約処理・演出完了・購読callbackは反映直前に現行戦闘との一致を確認する。
2. 戦闘sessionの `dispose` 相当を冪等にする。入力受付停止、非同期処理の無効化、既存の正規の演出abort／finalize、戦闘所有のlistener解除、音・資源の解放を、その所有者の契約に沿って行う。再接続に必要なpage所有資源は保持し、非表示中の入力・不要な描画を停止する。
3. 専用Workerは所有に応じて停止する。共有Worker・音・texture cacheは、別の利用者を壊さない管理にする。DOMを消すだけで処理を終えない。
4. 開始処理の途中で失敗した場合も、作成済みの資源と購読を片付ける。失敗したmountを次のmountの前提にしない。
5. 中断要求の扱いを定める。確定途中の操作を半分だけ止めず、現在のcommitと演出の扱いを分離する。保存可能な境界が得られるまでの入力停止と要求の完了通知を実装する。
6. CPU思考中、対象選択中、反転・移動・破壊演出中、結果待ち、ウィンドウの非表示・復帰で検証する。

**検証・完了条件**

- 再戦reset、中断、画面の最終破棄を別の操作として検証する。[board-renderer.ts](../../ui/board-renderer.ts) の `resetBoardVisualRenderSession` はpage所有資源を保持し、`destroyBoardVisualPageRuntime` は最終解放を担当する。`resetGame` の呼び出しだけを最終disposeの代用にしない。
- 現在のpage destroyは終端処理であり、その後のcontroller再生成を禁止する。同一ドキュメントの会話と戦闘の往復では呼ばず、本当のpage／host破棄時だけに使う。再生成可能なruntime ownerへ変更する場合は独立した設計変更として、同一ドキュメント内の再接続と最終解放を検証する。
- dispose後に旧戦闘の状態更新、入力受付、音・演出の再開、ホストへの完了通知が起きない。
- 遅れて返るCPU応答と旧演出finalizerが、次の戦闘の状態やロックを変更しない。
- 二重dispose・途中失敗・再接続でも、所有資源が基準状態へ戻り、listenerやtickerが接続回数に応じて増加しない。
- 中断・異常終了では勝敗や報酬を発行せず、新作側が再開／再戦／戻るを選べる状態になる。

### P5. 保存・復元と保存失敗の復旧

**作業**

1. 製品用の保存データを定義する。保存schema、ルール／catalog互換性、戦闘ID、解決済み条件、正本の盤面・cardState、完全な乱数checkpoint、ターン開始済みかを含む進行位置を扱う。
2. 対象選択のinstance／段階、追加手、特殊石・カードの識別子、効果counter、対戦を継続するCPUの必要な判断メモリーを調べる。物語進行・報酬受領記録は新作側の保存に持たせる。
3. 関数、DOM、Pixi object、timer、Worker、UIロック、途中のアニメーション、通信seat tokenを保存しない。ネットワーク公開snapshotや `snapshot()` の戻り値を無検証で製品セーブへ転用しない。
4. 保存点は正本の更新が完了した境界に置く。対象選択待ちも、状態が完結している境界なら保存する。演出中の要求は、最新の確定状態と対応する保存完了を返す方式に統一する。
5. 復元時はデータ検証・互換変換を一時状態で完了し、新しいruntimeへ取り込む。ドロー、ターン開始効果、報酬、既に済んだ音・演出を再実行しない。表示は復元した正本から再構築する。
6. 保存先のinterfaceを定め、ブラウザ用とテスト用を接続する。既存のデッキ保存は呼び出し元を移行し、失敗時に成功表示しない。新作側のファイル保存adapterはP7で接続する。
7. 書き込み途中の中断、容量不足、読み書き拒否、壊れたJSON、未知の将来版、欠けたカードIDを検出する。保存先の保証に合わせて世代・backup・commit方式を選び、直前の有効データへ戻れるようにする。
8. 初回形式のfixtureと互換方針を固定する。将来の形式変更時は旧fixtureを移行し、新形式しか読めない実装へ黙って置き換えない。互換性が保証できないルール変更は明示的に拒否する。
9. データの大きさ、配列件数、盤面寸法、数値の有限性と範囲を復元入口で検証する。[prng.ts](../../game/schema/prng.ts) の `{ seed, calls }` は復元時に呼び出し回数分の処理を行うため、対応する乱数方式と合理的な上限を定め、異常値で長時間停止しないようにする。上限は現在の有効な対戦を根拠なく拒否しない範囲とし、乱数方式自体の変更は別変更にする。

**検証・完了条件**

- 「連続実行」と「保存→全実行時資源を破棄→新runtimeで復元→同じ操作」を比べ、正本状態、乱数、効果回数、手番、勝敗が一致する。
- 対象選択途中、追加配置、ターン境界、終了済みで再開し、二重適用がない。CPUは既存の固定計算条件による比較と、実時間制約下の合法性・中断検証を区別する。
- 復元直後の盤面・手札・対象候補と入力が正本に一致し、音や報酬の重複がない。
- 保存失敗・互換性拒否が呼び出し元に届き、既存の対戦と有効セーブが残る。異常データを空の新規ゲームとして成功扱いしない。
- 既存のデッキ保存で失敗した場合も、未保存の編集を保持し、保存済み表示・保存済み状態への切り替えを行わない。

### 実装時のbuild・通常配信

TypeScript変更は型検査と必要なbuild、影響のある生成物には生成・同期検証を行う。プレイ可能なゲームを変更したフェーズは、最終ソースへ `npm run build:vite` を実行し、通常配信の `http://127.0.0.1:8000/` へ反映する。必要なWorker mirrorは `npm run worker:prepare` と `npm run check:worker-mirror` で扱う。

8000の既存正常サーバーを再利用し、所有プロセスと対象repo、最終HTTP 200、継続起動の根拠を確認する。ビルドのために8000を止めない。5174で `vite-dist/` を配信中なら、所有を確認してその競合を解決するまで同出力を再buildしない。一時テストサーバーだけは検証後に片付ける。本計画書のみの更新ではbuild・サーバー操作は不要。

## 7. 失敗時の戻し方とコミット単位

- P0の基準、P1の契約・検証、P2の入口、既存画面への接続、P3のホスト、P4の終了管理、P5の保存、P6の成果物は、依存が追える単位に分けてコミットする。
- 新入口の検証を終える前に現行入口を削除しない。移行完了後は不要な比較用分岐を片付け、恒久的な二重実装を残さない。
- 正本状態・乱数の不一致、演出と入力の不整合、旧戦闘からの書き込み、保存喪失、独立consumerの欠落が出たら、当該段階の採用を止める。最後に確認できたadapter／固定成果物を使い、原因を直して該当検証を再実行する。
- 新形式のセーブを旧版が読めない場合がある。コードの切り戻しとセーブの復旧を別に設計し、旧版で新データを上書きしない。
- 戻す対象は今回の変更だけとする。共有作業ツリーの一括reset、未追跡ファイル削除、他作業のrevertで復旧しない。ブランチ・worktreeはユーザーが依頼した場合に作る。
- テストの削除・skip・期待値緩和、比較対象からの重要状態除外で完了条件を満たしたことにしない。
