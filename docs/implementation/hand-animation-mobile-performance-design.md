# 手アニメーションのモバイル性能改善 設計

## 1. 文書の役割

この文書は、スマートフォンで配置・通常ドロー時の手がかくつく問題について、実測根拠、内部設計、完了条件を定める実装設計である。

- プレイヤー向け時間仕様の正本: `01-rulebook.md` と `正本/演出正本.md`
- 内部責務境界の正本: `docs/architecture-contracts.md`
- 実装対象: DOM-ownedの手演出と、その周辺の表示資源管理
- 非対象: canonical game state、`events[]` の順序、Pixi board writer、ゲームルール

## 2. 目的と範囲

スマートフォン相当の画面で、自分・相手の石配置と通常ドローの手がかくつく問題を根本経路で改善する。モバイルだけ演出を無効化せず、全端末が共有する配置・ドロー経路を直す。

配置約0.44秒、通常ドロー約0.56秒という既存テンポ、接触時の石確定、スポーン、反転、手の退避、入力再開の順序は変更しない。

## 3. 調査根拠

### 3.1 前回修正で解消した負荷

初回調査では、待機中5秒の `TaskDuration` は約1.4ms、DOM mutationは0であり、常時走るバックグラウンド処理は主因ではなかった。一方、配置手アニメーション1回につきカードUI側で53件のDOM mutationが発生していた。

前回修正では、手画像をactor別に再利用し、カードUIを差分更新した。継続配置のmutationは53件から15件、黒操作＋白CPU応答の手表示有無による差は106件から16件へ減少した。手スキンの再取得もキャッシュ済み経路では0になった。この修正はDOM・画像負荷には有効だったが、スマートフォン実機の見た目のかくつきは残った。

### 3.2 残存症状の再計測

Chromiumを844×390、device scale factor 3、CPU 6倍スロットルにして、起動処理完了後の配置・ドローを計測した。

- 配置・ドローともrAF間隔は最大約16.8ms、20ms超0回、LongTask 0だった。
- 配置は約450msで28フレームだったが、1フレームの最大移動量は約64.7 CSS px、95 percentileは約50.1px、24px超が9フレームあった。
- ドローは約566.6msで35フレームだったが、1フレームの最大移動量は約36.2 CSS px、95 percentileは約33.4px、24px超が7フレームあった。
- `#handLayer` と `#handWrapper` を毎回 `display:none` から復帰する通常配置は、CPU 6倍スロットルで `TaskDuration` 約141〜160ms、`RecalcStyleDuration` 約38〜50msだった。事前にmountを維持した比較では `TaskDuration` 約108〜148ms、`RecalcStyleDuration` 約22〜25msまで低下した。
- アニメーション終了後にラッパーへ残るWeb Animationsオブジェクトは増殖していなかったが、`fill: forwards` の最終アニメーションが1件残り、次回の初期transformより優先され得る状態だった。

したがって、残存症状の中心はフレーム落ちではなく、短い時間に長距離を強く前寄せ・後ろ寄せで移動するモーション設計と、演出ごとの描画レイヤー再構築が組み合わさった見かけ上の跳躍である。

## 4. 設計

### 4.1 長距離移動を滑らかな速度曲線にする

配置の接近・退避、ドローの搬送・退避には、平均速度から大きく外れない緩い対称曲線 `cubic-bezier(0.3, 0.2, 0.7, 0.8)` を共通利用する。

既存の配置接近は開始直後に距離を消費しすぎ、退避は終了直前に速度が最大になる。ドローも同様に搬送が前寄せ、退避が後ろ寄せだった。完全停止から始終するS字曲線は、固定された短い時間では中盤速度を平均の約1.5倍まで上げる必要があり、自分側の長距離配置で最大約35.9pxが残った。そこで始終端にも平均の約0.67倍の速度を持たせ、中盤を約1.14倍に抑える対称曲線にする。総時間と到着時刻を保ったまま、表示フレーム間の最大移動量とphase境界の速度差をともに抑えられる。

石を押し込む短いbobは `ease-in-out`、山札から持ち上げる短いpickupは `ease-out` のままとし、意味の異なる小動作は変更しない。

### 4.2 手レイヤーをmountしたまま再利用する

- 画面全体を覆う `#handLayer` は背景を持たない `pointer-events:none` のコンテナとして常時 `display:block` にする。全画面要素自体にはopacityや `will-change` を付けず、全画面合成面を作らない。
- 180px四方の `#handWrapper` だけを常時mountし、待機時は `opacity:0`、演出時は `opacity:1` にする。
- ラッパーには `contain: layout style paint`、`will-change: transform, opacity`、`backface-visibility:hidden` を指定し、レイアウト・paint範囲と合成資源を局所化する。
- 次回の初期transform、石、カード、actor画像を待機状態で準備し終えてからopacityを1にする。開始位置を準備する途中の1フレームを見せない。
- 配置・ドローの終了時はラッパーをopacity 0へ戻し、`display:none` にはしない。
- captureやカード使用など同じレイヤーへ一時要素を直接追加する経路も、終了時に要素だけを除去し、レイヤーはmountしたままにする。

### 4.3 終了済みアニメーションを明示的に破棄する

配置・ドローの開始前と終了後に `#handWrapper.getAnimations()` を列挙して `cancel()` する。これにより、前回の `fill: forwards` が次回のinline初期transformを一瞬上書きする経路をなくす。

リセット時も一時要素を除去し、ラッパーをopacity 0、display blockへ戻し、残留アニメーションを破棄する。

### 4.4 既存の資源管理と責務を維持する

- `#handImage` は画面側で同期済みの基準手スキンを保持し、演出中に `src` を書き換えない。
- CPU・相手・再生イベントなど別スキンを使う主体は、解決済み画像パス単位のactor画像を引き続き再利用する。
- 配置演出終了時のカード操作可否再同期と差分描画を残す。
- 手/HUDから盤面への軌道は既存どおりDOM presentation層に置き、盤面ピクセルのwriterを増やさない。

## 5. 採用しない案

- スマートフォンだけ手アニメーションを無効化する: 自分・相手で共有する通常経路の問題を残す。
- 配置・ドロー時間を長くする: 最大移動量は減らせるが、仕様上の短いテンポを変える。
- CSS効果だけを削除する: filter、shadow、backdrop-filter、DPRの比較でrAF最大値は有意に変わらなかった。
- 全画面の手レイヤーへopacityや `will-change` を付ける: 不要な全画面合成面を常駐させる可能性がある。
- UI再同期を削除する: 演出中に描画されたdisabled状態が入力再開後も残る危険がある。

## 6. 完了条件

1. 配置のtransform phase時間は208ms、78ms、156ms、ドローは109ms、280ms、171msのままである。
2. 自分・相手の配置とドローが共通の滑らかな長距離移動曲線を使う。
3. 844×390、device scale factor 3、CPU 6倍スロットルのwarm計測で、配置・ドローの1フレーム最大移動量が30 CSS px以下になる。
4. 同条件でLongTask 0、rAF最大間隔20ms以下を維持する。
5. 演出後も `#handLayer` と `#handWrapper` はdisplay block、ラッパーはopacity 0、ラッパーのactive animationは0になる。
6. actor再利用、`#handImage.src` 不変、配置接触時の確定、busy解除、入力再開の既存テストが通る。
7. ブラウザ実画面の配置中・ドロー中・終了後スクリーンショットで、開始位置のちらつき、二重表示、残像、操作UI欠落がない。

## 7. 自己レビュー

- プレイヤー向けの時間と意味順を変更しないため、`01-rulebook.md` と `正本/演出正本.md` の記述は現状のまま一致する。
- イージングはownerや端末で分岐させず、自分・相手、PC・スマートフォンの共有経路へ適用する。
- 常駐させる合成候補は180px四方のラッパーに限定し、全画面レイヤーは透明合成面にしない。
- `display:none` を期待するテストだけを書き換えるのではなく、opacity、残留Animation数、既存phase時間を回帰条件にする。
- 実装後に最大移動量30pxを満たさない場合は、完了扱いにせず曲線または座標経路を再設計する。

## 8. 実装後の検証結果

- 配置の接近・退避、ドローの搬送・退避を `cubic-bezier(0.3, 0.2, 0.7, 0.8)` へ統一し、phase時間は配置208ms・78ms・156ms、ドロー109ms・280ms・171msのまま維持した。
- `#handLayer` と180px四方の `#handWrapper` をmountしたまま再利用し、待機時はラッパーだけをopacity 0にした。通常完了、reset、timeoutで終了済みAnimationを破棄し、cancel後に後続phaseを再生成しないガードも追加した。
- 844×390、device scale factor 3、CPU 6倍スロットルのwarm計測結果は次のとおり。全経路で30px以下、rAF 20ms以下、LongTask 0を満たした。

| 経路 | 最大移動量 | p95移動量 | rAF最大間隔 | LongTask |
| --- | ---: | ---: | ---: | ---: |
| 自分側・配置 | 27.603px | 27.175px | 16.7ms | 0 |
| 自分側・ドロー | 26.311px | 26.068px | 16.8ms | 0 |
| 相手側・配置 | 5.631px | 4.536px | 16.8ms | 0 |
| 相手側・ドロー | 15.625px | 15.490px | 16.8ms | 0 |

- 各演出終了後はlayer/wrapperともdisplay block、wrapper opacity 0、active Animation 0だった。最終状態でもドロー一時カード0、layer直下一時要素0を確認した。
- 配置中、ドロー中、終了後のスクリーンショットを844×390のAndroid相当viewportで確認し、手の二重表示、開始位置のちらつき、残像、カードUI欠落は見られなかった。
- focused animation Jest、bootstrap reset Jest、no-animation Jest、TypeScript typecheck、browser/Vite build、asset case、Worker runtime preload、Worker mirror検証を実施した。`worker:prepare` のmirrorコピーではWindowsの一時的な `copyfile UNKNOWN` が発生したが、同じ生成スクリプトの再実行は成功し916ファイルのmirror一致を確認した。
