# ネット対戦モード 設計・計画・実行手順書

最終更新: 2026-02-14（再精査版）
対象: `othello_v2`

## 0. この手順書の前提（確定事項）

- 変更はローカル環境だけで完結させる。
- 追加の外部部品は使わない。もし必要になった場合は実装前に合意を取る。
- 起動の入口は `index.html` のみとし、入口を増やさない。
- ルール判定は `game/` 側に集約し、`ui/` 側で独自確定しない。
- UI再生は `events[]` の順番を守り、盤面の見た目更新は再生担当に一本化する。
- 常時動く `setInterval` は使わない（再接続確認は操作時や必要時の再取得で行う）。
- player / owner / 色の値は境界で正規化してから内部処理へ渡す。
- window / globalThis への新規公開は最小限にし、追加時は理由と参照先を記録する。

## 1. 目的

- 既存のCPU対戦を壊さず、同じ画面内でネット対戦を追加する。
- ルール判定と画面表示の責務を分離し、処理の重複と衝突を防ぐ。
- 段階ごとに確認できる手順を固定し、途中で迷わないようにする。

## 2. 完了条件

次をすべて満たしたら最小公開版を完了とする。

1. 同じ部屋番号に2人が参加できる。
2. 石置き・カード使用・パスが両画面で同順に反映される。
3. 順番違い、重複送信、版ずれが拒否され、盤面が壊れない。
4. 切断後の再接続で同じ局面へ復帰できる。
5. 既存CPU対戦とローカル2人対戦が後退しない。
6. `events[]` の再生順と単一書き手の原則が維持される。
7. 変更に応じた `01-rulebook.md` 更新が先行または同時に行われる。
8. ローカルの確認手順で再現できる記録が残る。

## 3. 全体設計

### 3.1 構成

- 画面層（操作と表示）
  - 役割: モード切替、入力受付、結果表示。
  - 対象: `index.html`, `ui/handlers/init.js`, `ui/*`。
- 進行層（ルール）
  - 役割: 手の妥当性判定、次局面生成。
  - 対象: `game/turn/turn_pipeline.js`, `game/logic/*`。
- 対戦管理層（新規）
  - 役割: 部屋管理、順番管理、重複防止、再接続復元。
  - 対象: `scripts/local-match-server.js`（新規）。

### 3.2 モード設計

- `cpu`（既存）
- `local`（同端末2人）
- `network`（ネット対戦）

方針:

- 操作はボタンで切替、URLは補助（部屋番号受け渡し）のみ。
- デバッグ用フラグは本番モード判定に流用しない。

### 3.3 衝突防止ルール

- 単一入力出口: 盤クリック・カード使用・パスを1つの入口に集約。
- 単一判定: 対戦管理層のみが手を確定。
- 単一描画: 再生中の盤面直接書き換えは禁止。
- 単一連番: `actionId` と `stateVersion` を必須にして重複/逆順を拒否。

## 4. データ設計（最小）

部屋状態:

```json
{
  "roomId": "ABCD1234",
  "stateVersion": 12,
  "currentPlayerKey": "black",
  "gameState": { "...": "..." },
  "cardState": { "...": "..." },
  "recentActionIds": ["local-10", "local-11"],
  "updatedAt": 1760000000000
}
```

操作データ:

```json
{
  "actionId": "local-12",
  "turnIndex": 12,
  "playerKey": "black",
  "type": "place",
  "row": 2,
  "col": 3
}
```

## 5. 段階計画（実装順）

## フェーズ-1: 仕様先行更新（実装前）

目的:
- 実装で変える挙動を先に一次情報へ反映する。

作業:
1. `01-rulebook.md` にネット対戦モードの挙動（入力、同期、拒否、復帰）を追記。
2. 既存UI/演出仕様と矛盾しないことを確認。

完了条件:
- 仕様更新内容に沿って実装できる状態になる。

## フェーズ0: モード土台

目的:
- 本番用モード切替をデバッグ切替から分離する。

作業:
1. `index.html` にネット対戦ボタン・部屋入力を追加。
2. `ui/handlers/match-mode.js`（新規）でモード状態管理を実装。
3. `ui/handlers/init.js` に初期化とイベント紐付けを追加。

完了条件:
- `cpu/local/network` を画面で切り替えられる。

## フェーズ1: 入力出口の一本化

目的:
- 入力経路重複をなくし、分岐を1か所へ寄せる。

作業:
1. `ui/diff-renderer.js` の盤クリック入口を共通入口へ接続。
2. `cards/card-interaction.js`（補助: `cards/card-interaction-effects.js`）のカード操作入口を同じ共通入口へ接続。
3. パス操作も共通入口へ接続。

完了条件:
- 盤・カード・パスが同じ入口を通る。

## フェーズ2: 対戦管理層（新規）

目的:
- 部屋と進行の確定を1か所に集約する。

作業:
1. `scripts/local-match-server.js` を作成。
2. 部屋作成、参加、状態取得、操作受付を実装。
3. `applyTurnSafe` で手を適用して統一。
4. 既存部品のみで実装し、追加依存を増やさない。

完了条件:
- 2画面で同じ部屋に入り、同じ結果を受け取れる。

## フェーズ3: 画面クライアント（新規）

目的:
- ネット対戦時の「送信→確定反映」を成立させる。

作業:
1. `ui/network-client.js`（新規）を作成。
2. 参加、同期、送信、再同期を実装。
3. 順番違い・重複・版ずれの拒否理由を表示。
4. 再接続確認は必要時再取得で行い、常駐監視を避ける。

完了条件:
- ネット対戦中は確定結果のみで盤面が更新される。

## フェーズ4: 既存依存の置換

目的:
- `DEBUG_HUMAN_VS_HUMAN` 依存を通常モード判定へ置換する。

対象（優先順）:
1. `game/turn-manager.js`
2. `game/move-executor.js`
3. `ui/board-renderer.js`
4. `ui/diff-renderer.js`
5. `cards/card-renderer.js`
6. `cards/card-interaction.js`（補助: `cards/card-interaction-effects.js`）

完了条件:
- 本番モード切替にデバッグフラグが不要になる。

## フェーズ5: 再接続・整合

目的:
- 切断後の復帰と版ずれ回復を安定化する。

作業:
1. 再接続時に最新状態を取得して再描画。
2. 版ずれ時に自動再取得。
3. `actionId` と `stateVersion` で重複送信を抑止。

完了条件:
- 片側再読み込み後に局面が一致する。

## フェーズ6: 最終確認と記録

目的:
- 実装と仕様の整合を確定し、再現手順を残す。

作業:
1. 変更箇所に応じて `01-rulebook.md` 追記を最終確認。
2. テスト実行。
3. 再現手順と確認結果を `docs/` に記録。

完了条件:
- 仕様と実装の差異が説明可能で、確認手順で再現できる。

## 6. 実行手順（ローカル）

### 6.1 準備

```powershell
npm install
```

### 6.2 起動

画面配信:

```powershell
npm run serve
```

対戦管理層:

```powershell
node scripts/local-match-server.js
```

確認:

- 画面Aで部屋作成
- 画面Bで同じ部屋参加

### 6.3 テスト順序

まず全体:

```powershell
npm test
```

変更範囲の再確認:

```powershell
npm run test:jest:changed
```

## 7. 受け入れチェック

- [ ] `game/` から `ui/` を直接参照していない。
- [ ] `ui/` が `game/` の内部実装へ依存していない。
- [ ] UI注入の出口が `ui/bootstrap.js` 以外へ分散していない。
- [ ] UI再生が `events[]` の順序どおりである。
- [ ] 再生中の盤面直接書き換えが発生していない。
- [ ] ネット対戦時にCPU自動処理が誤発火しない。
- [ ] 重複送信・順番違い・版ずれで局面が壊れない。
- [ ] 常駐 `setInterval` を新規追加していない。
- [ ] 既存CPU対戦が後退していない。

## 8. 想定リスクと回避

- リスク: デバッグ依存が残る。
  - 回避: 対象ファイルを優先順で置換し、残存検索を毎回実施。
- リスク: 同じ手が二重で反映される。
  - 回避: `actionId` / `stateVersion` 必須化と拒否時再同期。
- リスク: 演出再生と再描画が競合する。
  - 回避: 既存の再生完了待ち経路へ統一。
- リスク: 値の表記揺れで判定がずれる。
  - 回避: 境界で値を正規化して内部形式を統一。
